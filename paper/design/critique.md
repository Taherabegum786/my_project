# Design critique of EMBER (Design Critic, 2026-11-05)

Role: a tough but fair reviewer for IEEE Access or Computer Networks. Inputs: `BRIEF.md`, `design/design.md`, `design/experiment_spec.md`, `scout/scout_A.md`, `scout/prior_work.md`, `scout/feasibility.md`. I checked tooling on this VM: Go 1.24.7 is present, and `go get github.com/cloudflare/circl@v1.6.1` works through the proxy, so ML-DSA is available in Go. The venv has no aiohttp. There is no wrk, ab or hey.

Severity scale:
- **S1** is reject-level if not fixed.
- **S2** is a major revision.
- **S3** is a minor revision.

The status column says how the design was changed. Each fix is logged in design.md under "Critic changes log" (D-numbers) and in `experiment_spec.md` §7.

## Summary verdict (as a reviewer would write it)

> The topic is new (no PQ work on CDN signed URLs or cookies). The writing is honest about HMAC and HNDL. But the core mechanism is a known primitive: Merkle batch signatures, MTL mode, MTC. The evaluation compares that primitive mostly with *naive* per-token signatures, which are strawmen. The strongest competitors are absent: per-domain multi-MAC, short-lived delegated keys, KEM-wrapped epoch MAC keys, MTL mode itself, and per-token signatures with a verification cache under HTTP/2 header compression. The fleet evaluation is a simulator checked against a second simulator built on the same assumptions, so it is circular. The controller contribution may vanish in the stapling/push regime, which the design itself recommends. Major revision at best in the current form.

## S1: reject-level issues

| # | Issue | Why a reviewer rejects | Fix applied |
|---|---|---|---|
| 1 | **Novelty: "just batch signatures / MTL applied to tokens."** Contribution C2 is the CT-RSA'24 batch-signature construction, an instantiation of it. MTL mode already provides "condensed signature = path to a signed rung" plus separately distributed rungs. | Contributions C2 and C5 alone read as an engineering profile. | D1: C2 is reframed explicitly as a *profile/instantiation*. The headline moves to the CDN-specific systems contributions (C3 dissemination, C4 epoch control, the new real-prototype evidence C6, and the head-to-head with the strong baselines). **MTL mode is added as a baseline (B13)**, with a stated structural delta (independent per-epoch trees vs. a growing series, and the effect on root-cache state and miss behaviour). "First threat model" is softened to "a threat model". |
| 2 | **Strawman baselines.** Only HMAC and per-token signatures are compared. Missing: **(a)** multi-MAC tokens with one tag per verifier domain (CDN/region), which removes the multi-CDN argument; **(b)** short-lived Ed25519 epoch keys certified by ML-DSA (the delegated-credentials pattern), which gives ~90-B tokens with the same dissemination structure as EMBER; **(c)** KEM-wrapped per-epoch HMAC keys pushed to edges (ML-KEM-768), which bounds what edge compromise yields to the current epoch; **(d)** ML-DSA per token **with an edge verified-token cache**, so the per-request cost is paid once per session per edge; **(e)** ML-DSA split across multiple cookies; **(f)** MTL mode; **(g)** macaroons and TLS-bound or DPoP tokens, at least qualitatively. | R1 and R2 are only "wins" against naive baselines. The fit analysis allows multi-cookie splitting. A new E3b measures **real HPACK/QPACK-style header bytes per session** with Go's `x/net/http2/hpack`. Per-token baselines get a `+vcache` variant in E2, E8 and the sim. Hypotheses H1, H2 and H8 are re-stated against the *strongest* baseline, not the naive one. |
| 3 | **Circular evaluation.** fleet_mc is "validated" by a DES with the same workload, the same RTT model and the same miss semantics. The analytic M(Δ) is then "validated" against the simulator. No real system is ever measured beyond crypto microbenchmarks. This is lesson 5 from the prior rejection. | "Simulation validating its own model" | D3: a new **E8 real prototype in Go** (edge verifier, issuer + root service, open-loop load generator) on loopback with pinned cores, real token issuance and verification, and real root fetches with injected root-service delay (netem is unavailable, so the delay is applied in userspace and stated as such). E8c runs the *same* small configuration through fleet_mc and the analytic model, and the simulator is validated against **real measurements**. The DES-vs-MC check stays as an internal consistency check only and is labelled that way. |
| 4 | **The controller contribution (C4) can collapse.** In the design's own words, with push or stapling F_miss → 0 and the optimum becomes Δ_min. Pull misses fall only on the first request of a session with ~150 segments, so miss latency per request is tiny. The "adaptive" policy is an argmin over a 25-point grid; a reviewer will say "trivial". | A contribution that may produce a null result, with no oracle comparison | D4: the controller is evaluated against an **oracle best-fixed-Δ chosen in hindsight per tenant class** and against WC. ## S2: major-revision issues

| # | Issue | Fix applied |
|---|---|---|
| 5 | **Over-stated G2/edge-compromise benefit.** A compromised edge can already serve anything it caches without checking tokens. Asymmetric tokens only stop *lateral* minting (tokens usable at other edges, other CDNs, other tenants' paths). The design does not say this. | D5: the threat model now says so explicitly. The benefit is framed as "blast radius" and quantified in Table V: which verifiers a single compromised edge can mint for, under each scheme. |
| 6 | **Tenant pooling silently changes the trust model.** One CDN-operated issuer key signs pooled trees for many tenants, so the CDN can mint for every tenant. That contradicts motivation #2 (multi-CDN, owner-held key). | D6: pooling is restricted to "issuer-as-a-service where the tenant already trusts the CDN with minting". Pooled leaves include Tenant in the claims and a tenant-id in the tweak. This is evaluated separately and flagged in the limitations. |
| 7 | **Privacy/linkability not analysed.** (a) N_e in the public, cacheable signed root leaks **per-tenant issuance volume** (business intelligence) to anyone. (b) (e, i) reveals issuance time and order. (c) Every token in an epoch shares a root; a common (e, i) is a stable per-token identifier across all segment requests (same as status quo, but say so). (d) The root-fetch timing at an edge reveals whether *someone* recently received a token from that tenant (cache-probing side channel). | D7: §4.6 gains a "Privacy and side channels" paragraph. Mitigations: pad to 2^d, or bucket N to a power of two, plus dummy leaves; pooling; publishing roots only via stapling and push (no public pull) for volume-sensitive tenants. E2 measures the cost of padding (size is unchanged; issuer hashing is ≤ 2×). |
| 8 | **Replay and binding.** Bearer replay is "out of scope", but a reviewer expects it to be analysed: cross-edge replay, cross-epoch replay, token sharing, and cross-tenant replay in pooled trees. Clock skew between issuer and edges against the T_start + Δ + V_max rule is missing. | D8: a security-analysis checklist is added (replay classes, binding options IP/ASN, DPoP-style key hash, TLS-exporter binding as future work, skew tolerance τ_skew with a test). New negative tests cover cross-tenant leaf reuse in a pooled tree and a skewed clock. |
| 9 | **Proof sketch is loose.** It names "SM-TCR/2nd-pre", leaves the multi-target bound and reduction loss implicit, and the 4-byte epoch and index can wrap. The chosen-claims oracle lets 𝒜 pick c before r, so the argument must say why r after c defeats pre-computation. The hybrid "both must verify" AND-combiner needs a citation (the prior paper was criticised exactly on hybrid definitions). | D9: the theorem is restated as SM-DSPR/SM-TCR per the SPHINCS+ tweakable-hash framework, with an explicit query count q_h and target count. The epoch/index wrap is forbidden (kid rotation before 2^32). The ordering argument is spelled out (salt chosen after claims). The hybrid is an AND-combiner citing Bindel et al. [TODO-verify]. Still a sketch; no new full proof is claimed. |
| 10 | **Measurement methodology.** (a) The Python EMBER path verify is (d+1) interpreter-bound hashlib calls, so the comparison with Python HMAC measures interpreter overhead. (b) Iterations inside one process are not independent replicates. (c) Three different native stacks (OpenSSL 3.6+oqsprovider in Docker, circl in Go, pqcrypto) could be mixed without labels. (d) There is no control of VM frequency/noise. (e) `openssl speed` gives means only. | D10: the primary CPU numbers come from **native/Go**; Python is shown only as a secondary panel. Statistics: ≥ 5 independent process runs × ≥ 2000 iterations; the CI is a bootstrap over run-medians (plus the pooled-iteration CI); warm-up 200 iterations + 1 s; pinned cores; the governor and steal time are recorded. Every timing row carries an `impl` label. Cross-implementation sanity: circl ML-DSA-44 verify must be within 3× of the OpenSSL native figure, otherwise investigate. |
| 11 | **Statistics in the simulation.** "5 replicates, mean ± 95% CI" uses a normal approximation without saying so, and has no paired comparison. | D11: ≥ 5 seeds (10 for the controller headline), Student-t 95% CI (t₄ = 2.776), common random numbers across policies, paired-difference CIs for every "A beats B" claim, and claims made only when the CI excludes 0. |
| 12 | **Compute feasibility.** Fixed Δ = 0.01 s × 24 h × 1000 tenants gives ~8.6·10⁹ tenant-epochs per run. λ̄ = 20000 × 24 h gives 1.7·10⁹ tokens per replicate. With 5 modes × 7 policies × 5 reps this does not fit "≤ 3 h on 4 cores". | D12: an explicit compute budget (spec §5.1). The Δ sweep uses 1 h stationary horizons. The controller uses 24 h only at λ̄ ≤ 2000, and λ̄ = 20000 runs 1 h of peak. Empty tenant-epochs are never materialised (the simulation iterates over arrival events binned with searchsorted). A guard: run QUICK first, extrapolate wall time, and cut horizons, recording the cut in `sim_params.json`. The E8 prototype is capped at ~45 min wall time. |
| 13 | **Fit analysis is self-fulfilling.** "100% of EMBER tokens fit" holds by construction (the count trigger enforces the budget). The fit table also ignores multi-cookie splitting and HPACK. | D13: E3 now reports *bytes per session on the wire* (E3b, HPACK-encoded) and *upstream bytes per session*. Fit fraction is kept but called a sanity check. The multi-cookie variant is included. |

## What the paper can honestly claim after the fixes
- EMBER is a CDN profile of Merkle batch signatures with CDN-specific dissemination and epoch control. It is evaluated on real measurements (crypto + a Go prototype under load) and a simulator validated against that prototype.
- It is **the only scheme in the comparison that is simultaneously** (i) PQ-secure without a time-bounded classical assumption, (ii) free of minting secrets at edges, and (iii) a cookie/URL-friendly token. B11 (short-lived Ed25519) is smaller but relies on "no CRQC breaks Ed25519 within the key lifetime". B12 (KEM-wrapped MAC) puts a short-lived minting secret on every edge. B5+vcache with HTTP/2 may be competitive on CPU and bytes for cookie transport. **The paper must report this honestly if the data shows it.**

## Defences against the prior paper's rejection reasons (coordinator request)
| Prior reason | Defence now in the spec |
|---|---|
| Implausible numbers | Sanity bounds (ML-DSA verify in tens to hundreds of µs). Cross-implementation 3× check. `notes_impl_xcheck.md`. |
| Interpolated or projected results | Reporting rule: model = labelled line, data = markers. No table values without a producing script. |
| Marginal, implementation-level contribution | Reframed onto a protocol plus fleet dissemination and control, against strong baselines. The primitive is credited to prior work. |
| Client and server on one host over loopback | E8 uses 3 netns + 2 `tapbridge` instances (reused from `origin/claude/brave-meitner-l8yswp`) and pinned disjoint cores. A loopback fallback must be labelled. The single-VM limitation is stated. |
| Unjustified metrics | D(Δ) in seconds, no weights. % fit demoted. Bytes per session measured. |
| HNDL confusion | Kept the explicit "no HNDL for authentication" statement. |
| Issuer cost credibility | Native OpenSSL 3.5.4 (scratchpad build), 5 runs × 2000 iterations, bootstrap CIs over runs. |
| DO-NOT-REPEAT #3 (RTT/initcwnd model) | E8 explicitly does not sweep initcwnd, CC or loss, and has no handshake RTT model; TLS is omitted. |
