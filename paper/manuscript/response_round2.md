**Detail for item 2 (M2 recovery path and staple unit).** The new "Recovery" paragraph in §IV-A specifies the following.

- **Staple unit.** The client staples on the **first request of each connection**. A connection is used because clients can observe connections but not edges. The abstract, introduction, Fig. 1, §IV-C (where staple-all is now defined per connection), §VII-A and the conclusion all use this unit. In our workload a session uses one connection per edge, so per-connection stapling equals the simulator's "every new edge contact". §IV-C says so.
- **Miss path.** An edge with no valid entry (after eviction, a process restart or an unshared cache) answers 401 with a `Staple-Required` hint, and the client retries the same request with the signature. The prototype already implements this as a 403 with `X-Reject: staple required` (`proto/edge/main.go`).
- **Cost of one recovery.** One client–edge RTT (20.98 ms in our testbed), a 3,242-B HTTP/1.1 header line, and one ML-DSA-44 verification (100.9 µs).
- **Edge state.** 24 B per entry (16-B key plus 8-B expiry, from the prototype's map type; hash-table overhead excluded), held for at most V_max. New (token, edge) pairs arrive at 165.8/s and 1,658/s at the busiest simulated edge, which bounds the edge state at 0.60 M entries / 14.3 MB and 5.97 M entries / 143 MB.
- **When recovery is needed.** Only when an edge loses an entry for a connection that is still open. Its frequency was not measured, which Limitations states.
- **Qualified claims.** The availability claim (§IV-C, §VII-A rec. 2) now says that M2 and staple-all EMBER depend on edge cache retention or on the recovery retry. Rec. 2 ("fixes the edge") cites the recovery path.
